# Skill Resolver Protocol

## Purpose

This document defines how the Gentle AI orchestrator resolves and injects skills into sub-agent prompts. It is the runtime contract for skill loading.

## Resolution Flow

### 1. Session Start (Once per session)

1. Orchestrator reads `.atl/skill-registry.md` (generated by `skill-registry` skill)
2. Parses registry into index: `skill_name -> { trigger, scope, path }`
3. Caches index in memory for session duration

### 2. Sub-Agent Launch (Each delegation)

When launching a sub-agent (via `task` tool), orchestrator:

1. **Matches skills** by:
   - **File context**: extensions/paths the sub-agent will touch (e.g., `*.tsx` → `react-patterns`, `*.py` → `django-expert`)
   - **Task context**: what the sub-agent is asked to do (e.g., "write test" → `python-testing-patterns`, "create component" → `react-patterns`)

2. **Selects matching skills** from registry (project-level preferred over global)

3. **Injects skill paths** into sub-agent prompt as:
   ```markdown
   ## Skills to load before work
   - .agents/skills/react-patterns/SKILL.md
   - .agents/skills/django-expert/SKILL.md
   - .agents/skills/python-testing-patterns/SKILL.md
   ```

4. **Instructs sub-agent**: "Read these exact files BEFORE task-specific work"

### 3. Sub-Agent Execution

Sub-agent MUST:
1. Read each injected `SKILL.md` file completely
2. Apply its rules, patterns, templates
3. Return `skill_resolution` field in result:
   - `paths-injected` = all skills loaded successfully
   - `fallback-registry` = registry not found, used fallback
   - `fallback-path` = skill path not in registry, guessed
   - `none` = no skills matched

## Skill Matching Rules

| Sub-Agent Task | File Context | Matched Skills |
|----------------|--------------|----------------|
| Create React component | `*.tsx`, `components/` | `react-patterns`, `accessibility` |
| Write custom hook | `hooks/*.ts` | `react-patterns`, `python-patterns` (for types) |
| Build form with validation | `schemas/*.ts`, `components/forms/` | `react-patterns` (RHF+Zod) |
| TanStack Query usage | `api/*.ts`, `hooks/use*.ts` | `react-patterns` |
| Write Vitest/RTL test | `*.test.tsx`, `*.test.ts` | `python-testing-patterns`, `react-patterns` |
| Django model/view/serializer | `models/*.py`, `views/*.py` | `django-expert`, `django-patterns` |
| Django security review | `settings/*.py`, `middleware.py` | `django-security` |
| Django + React integration | `vite.config.ts`, `api/client.ts` | `django-react-integration` |
| Bash script / CI/CD | `*.sh`, `.github/workflows/` | `bash-defensive-patterns` |
| Python code / refactor | `*.py` (non-Django) | `python-patterns` |
| SEO / meta tags | `*.html`, `index.html`, SSR pages | `seo` |
| Accessibility audit | any frontend file | `accessibility` |

## Priority Order (when multiple match)

1. **Project-level skills** (`.agents/skills/`) — highest priority
2. **Global skills** (`~/.config/opencode/skills/`) — fallback
3. **Most specific match** — e.g., `django-security` over `django-expert` for security tasks

## Deduplication

- Same skill name in both scopes → **project-level wins**
- Same skill in multiple global locations → **first in scan order wins**
- `_shared`, `sdd-*`, `skill-registry` → **excluded from injection** (support only)

## Verification

After delegation, orchestrator checks `skill_resolution` in result:
- `paths-injected` ✅ → continue
- `fallback-*` ⚠️ → re-read registry, re-inject on next delegation
- `none` ❓ → expected for tasks with no skill match
