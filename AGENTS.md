# AGENTS.md — Convenciones de ControlFit

Instrucciones para agentes de IA (y para cualquier colaborador) que trabajen en este repositorio.

---

## Regla dura: máximo 250 líneas por archivo

**Ningún archivo de código supera las 250 líneas.** Sin excepciones para archivos nuevos.

Aplica a todo el código fuente:

- Componentes React (`.tsx`), hooks, utilidades y tipos (`.ts`).
- Tests (`.test.ts` / `.test.tsx`).
- Módulos Python (`.py`).

Cuando un archivo se acerca al límite, partilo **por responsabilidad**:

- **React**: extraé subcomponentes presentacionales (ej. `gimnasioReact/src/pages/admin/calendario/eventForm/`), hooks por responsabilidad (ej. `memberForm/`) o helpers puros (ej. `utils/apiError.ts`).
- **Django/Python**: extraé acciones/servicios a módulos dedicados (ej. `gimnasioApp/views/membership_actions.py`) y tests a archivos enfocados (ej. `gimnasioApp/tests/test_operation_log_*.py`).
- **Tests**: dividí por caso de uso en archivos chicos y enfocados.

### Cómo se hace cumplir

- **Frontend**: regla ESLint `max-lines` (`max: 250`) como **error** en `gimnasioReact/eslint.config.js`. Se corre con `npm run lint` (desde `gimnasioReact/`).
- **Deuda técnica**: los archivos que ya superaban el límite al introducir la regla están listados en `LEGACY_LONG_FILES` (mismo archivo) y quedan eximidos temporalmente. **No agregues entradas nuevas**; cuando refactorices uno, sacá su entrada de la lista.
- **Backend**: todavía sin enforcement automático; aplicá la regla manualmente.

## Verificación antes de dar por cerrado un cambio (frontend)

Desde `gimnasioReact/`, correr el gate completo:

```bash
npx tsc -b        # typecheck
npm run lint      # eslint
npm test          # vitest
```

## Commits

Regla dura: **Conventional Commits**, con la descripción **en español** y **sin atribución a IA** (nada de `Co-Authored-By`, `Generated by` ni similares).

Formato:

```
<tipo>(<scope>): <descripción en español>
```

Tipos permitidos: `build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`, `refactor`, `revert`, `style`, `test`.

Ejemplo: `feat(calendario): agregar a11y al formulario de tipo de evento`

### Cómo se hace cumplir

Hook versionado en `.githooks/commit-msg` (vive en el repo, no en `.git/hooks/`). Activarlo una vez por clon:

```bash
git config core.hooksPath .githooks
```

El hook rechaza el commit si el asunto no cumple el formato. Ignora `Merge*`, `Revert*`, `fixup!` y `squash!`. `.gitattributes` fuerza `eol=lf` en `.githooks/**` para que el script funcione en Windows.

## Aprobación antes de commit y push (regla inquebrantable)

- **Ningún `git commit` se ejecuta sin visto bueno explícito del usuario** ("aprobado", "visto bueno", "dale") en la sesión.
- **Ningún `git push` se ejecuta sin visto bueno explícito del usuario**, incluso si el commit ya fue aprobado.
- Antes de pedir aprobación, el agente/colaborador debe mostrar: archivos a commitear, diff resumido y resultado del gate de verificación.
- Si el usuario no aprobó, detenerse y esperar. No "asumir" aprobación por silencio ni por mensajes ambiguos.
- Esta regla aplica también en modo automático: la automatización no salta la aprobación humana.

### Gate de verificación (obligatorio antes de pedir aprobación)

- Frontend: desde `gimnasioReact/`, `npx tsc -b`, `npm run lint`, `npm test`.
- Backend: `python manage.py test gimnasioApp` (y `python manage.py check`).
- Ningún commit se propone si el gate falla. Arreglar primero.

## Código legible para un junior

Todo código nuevo o modificado debe poder ser **explicado y modificado por un desarrollador junior sin ayuda**. Concretamente:

- **Una responsabilidad por función/módulo**. Si no cabe en ~30 líneas, partilo.
- **Máximo 2-3 niveles de anidamiento**; usá early returns y guard clauses.
- **Nombres que expresan intención**: sin abreviaturas crípticas (salvo convenciones del dominio como `gimnasio`, `miembro`).
- **Sin trucos**: nada de one-liners clever, metaprogramación ni cadenas funcionales largas si una versión explícita es más clara.
- **Comentarios explican el PORQUÉ**, no el QUÉ; en español para lógica no obvia. Si el código necesita un comentario para explicar qué hace, renombrá o refactorizá.
- **Patrones avanzados** (genéricos complejos, higher-order components, decoradores) solo si hay una razón documentada en el PR.
- **Prueba de junior**: si un junior no puede explicar el cambio en 2 minutos, refactorizá antes de commitear.
- **Consistencia sobre novedad**: seguí los patrones existentes del repo (camelCase en campos, `db_table` en Meta, comentarios en español) en vez de introducir estilos nuevos.

## Ramas, PRs y tamaño de cambios

- **No commitear directo a `main`**: usar rama + PR. Excepción: fixes triviales documentados.
- **Nombre de rama**: `<tipo>/<scope-corto>` (ej. `feat/calendario-a11y`, `fix/token-refresh`).
- **Un concern por PR/commit**. Si el cambio supera ~400 líneas modificadas, partilo en PRs encadenados (ver skill `chained-pr`).
- **PR en español**: qué cambió, por qué, cómo probar, riesgos y rollback.
- **PRs pequeños y enfocados** se revisan mejor y se revierten más fácil.

## Testing

- **Comportamiento nuevo requiere tests**; un bugfix requiere test de regresión.
- **Strict TDD** cuando `openspec/config.yaml` lo indica (backend: `python manage.py test gimnasioApp`).
- **No deshabilitar ni saltear tests** para que pase el gate; arreglar la causa.
- **Tests legibles**: un test por comportamiento, nombres descriptivos en español, sin lógica compleja en el test.

## Documentación y trazabilidad

- Actualizar `README.md` si el cambio es visible para el usuario o altera instalación/configuración.
- Actualizar specs en `openspec/` si cambia un contrato de API o una regla de negocio.
- Registrar decisiones no obvias en engram (`mem_save`) o en el PR.
- **Sin atribución de IA** en commits, PRs ni código (nada de `Co-Authored-By`, `Generated by`).

## SDD y skills del proyecto

- Al ejecutar cualquier fase SDD (`/sdd-*`), **apoyarse en las skills disponibles en `.agents/skills/`** relevantes al área tocada, cargando su `SKILL.md` antes de implementar y siguiendo sus patrones.
- Mapeo mínimo: frontend (React/TS) -> `react-patterns`, `accessibility`, `frontend-design`; frontend público/marketing (SEO) -> `seo` (condicional); backend (Django/DRF) -> `django-expert`, `django-patterns`, `django-security`; integración Django+React -> `django-react-integration`; testing -> `python-testing-patterns`, `python-patterns`; scripts/automatización -> `bash-defensive-patterns`.
- No reimplementar patrones que ya están documentados en esas skills; si una skill cubre el caso, seguirla.

## Hooks de verificación

Además del `commit-msg`, hay dos hooks versionados en `.githooks/`:

- **`pre-commit`**: bloquea archivos nuevos de código con más de 250 líneas y corre typecheck + lint del frontend si hay cambios en `gimnasioReact/`.
- **`pre-push`**: corre `python manage.py check`, `python manage.py test gimnasioApp` y, si existen dependencias instaladas, el gate completo del frontend (`tsc`, `lint`, `test`).

Se activan una vez por clon:

```bash
git config core.hooksPath .githooks
```

Escape hatch solo para emergencias: `SKIP_GATE=1 git commit` / `SKIP_GATE=1 git push`. **No es una forma de saltear la aprobación humana**, que sigue siendo obligatoria.
